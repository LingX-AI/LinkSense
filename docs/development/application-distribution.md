# 应用分享、上架与安装更新

应用卡片的三点菜单提供两个独立入口：“组织内共享”和“申请上架”。卡片底部不再显示“发布与分享”，也没有独立的发布版本操作。两种表单均在提交时保存应用内容和版本号。

使用说明和上架的版本说明均为选填。使用说明默认回显最近一次保存的内容，可修改或清空；组织内共享和申请上架共用这份初始说明，已发布版本的内容仍保持独立。保存或提交成功后关闭弹窗并刷新应用数据，失败时保留弹窗和输入内容。

插件中心右上角提供“我的发布”入口，统一管理当前用户提交的应用、插件和技能；发布页通过“返回插件中心”回到原分类。“申请上架”按应用、插件、技能选择来源。应用条目显示最近一次提交的版本、使用方式、审核及上架状态，点击“管理上架”可查看历史记录并继续更新或管理上架。

`GET /application-center/mine` 只返回当前组织用户拥有且未删除的应用，每个应用返回最近一次提交；待审核、未通过、撤回、下架和管理员停用的记录均保留展示。历史发布记录直接读取现有数据，无需重新提交。交互式应用的有效使用方式统一限制为服务；历史仅允许安装的记录不会因此获得服务权限。

## 版本号规则

两个表单默认填入当前最高版本号；首次提交默认使用应用包版本或 `1.0.0`。输入框提供固定的 `v` 前缀，版本号使用语义化版本比较，例如 `v1.10.0` 高于 `v1.9.0`。输入为空或格式无效时不能提交。

- 高于已有最高版本：正常提交。
- 等于已有最高版本：输入框下方提示版本号已存在，仍可提交。
- 低于已有最高版本：输入框下方提示并阻止提交；后端在事务内再次校验，阻止并发提交绕过限制。

版本号是展示标识，内容提交保持不可变。同号且内容未变时复用原记录；同号修改内容时保存新记录，已安装应用仍可发现更新。版本比较范围包含组织共享和上架申请的全部已有版本，撤回或拒绝申请不会删除其历史版本。

## 两个分发渠道与两种使用方式

- 组织内共享：填写版本号、使用说明，选择成员或用户组，无需审批。每条共享关系独立选择“应用安装包”“应用服务”，至少一种。已有共享对象时可以直接保存内容更新。成员与多个用户组的权限按同一渠道合并。
- 申请上架：填写版本号、使用说明、使用方式与版本说明；管理员审批通过后组织成员可见。新申请等待审核时，现有上架版本继续提供服务。管理员可停用上架项，发布者不能自行恢复管理员停用的上架项。
- 安装包：仅普通应用支持。复制成安装者拥有的独立应用，插件、技能保存为独立资源。不会复制创建者的凭据、凭据绑定、知识库或 MCP 连接；安装者按使用说明配置自己的资源。
- 应用服务：不安装副本，通过创建者配置的资源运行。只获得安装权限不能运行服务；服务权限不会授予包内容或凭据读取权限。

两个渠道的使用方式互不替代。应用中心始终使用当前批准的版本；直接共享使用作者最近一次保存共享时的版本。申请上架不会改变组织内共享的内容，也不要求先进行组织内共享。编辑草稿不改变已共享服务。任务记录保存创建渠道，后续执行、交互页面票据和知识访问继续检查该渠道的服务权限。正在执行的任务沿用入场时的版本快照。

交互式应用仅提供在线服务，不允许新建副本或通过源应用复制升级。后端共享、上架和安装接口均执行此限制，历史授权中的 `install` 不生效但不会自动提升为 `service`。已有独立副本不删除，继续使用自己已有的资源；已有普通应用的安装及更新行为不变。

## 交互式应用资源声明

`manifest.json.dependencies` 按 `plugins`、`skills`、`mcp_servers`、`knowledge_bases` 声明 `{id,name}`；`id` 为资源 UUID，`name` 仅作为匹配提示。UUID 统一转为小写，插件与技能合计最多 50 项，MCP 与知识库各最多 20 项。

导入预览按所有者、类型和可用状态进行精确匹配，可手动选择同类资源或留空。未匹配不阻止导入；声明和 `{type,id,resource_id:null}` 会保存。后续可通过应用菜单补配。声明及映射均不包含凭证，也不授予额外权限。

映射保存在应用草稿的 `interactive_dependency_bindings` JSONB 字段，实际资源仍使用既有三类应用绑定表。两者在同一事务内更新，使用草稿修订时间检查冲突。更新包保留相同声明的映射（含留空），新增声明尝试匹配，移除声明解除绑定。运行草稿和发布前检查全部声明；已发布版本仍使用不可变的实际资源快照，不受未完成草稿影响。

接口包括导入预览 `POST /applications/interactive-import/preview`、候选资源查询 `GET /applications/interactive-dependency-options`、应用资源配置 `GET/PATCH /applications/:id/interactive-dependencies`。导入和更新包接受可选 multipart 字段 `dependencies`，值为 `{"bindings":[{"type":"skill","id":"声明 UUID","resource_id":null}]}`。未提供的条目遵循自动匹配或保留原映射规则。

## 发现新版与手动更新

新安装的应用记录来源、渠道、安装版本及合并基线。列表显示“发现新版”，安装者可以查看更新说明并主动更新；仅发现版本不会改写已安装应用。组织内安装发现最新共享内容，应用中心安装仅发现最新批准内容。版本号相同但内容有变动也能发现更新。

普通应用更新采用三方比较：安装后未修改的名称、指令及模型选择接受上游变化，自行修改的值保留。插件和技能内容按文件摘要比较；保留个人修改、移除选择、新增的绑定与凭据。知识库和 MCP 配置保留，新增的资源要求需要安装者补充配置。

安装者再次共享自己的应用时，更新先修改个人应用配置；需要保存组织内共享，或重新申请上架并审批通过，才会更新相应渠道的服务。源应用撤销分享、下架、停用或删除后，不再授权新的安装/更新/服务调用；已安装应用和历史任务保留。

## 存储与升级

迁移 `20260916090000_interactive_dependency_bindings` 只新增 JSONB 列，既有记录默认 `[]`，不删除或改写历史资源、应用包、共享与版本快照。部署时先迁移数据库，再更新 API。没有资源声明的旧包继续可用；历史交互式安装权限的收紧及恢复为服务权限的操作见上文。测试示例位于 `examples/interactive-dependency-check/`，包含初始包与更新包的构建脚本及手动检查清单。

迁移 `20260916030000_add_application_distribution` 已按维护者确认的规则保留历史数据：

1. 旧共享默认转换为 `service`；旧应用 `allow_copy = true` 的共享转换为 `install + service`。
2. 移除 `applications.allow_copy`，新增按共享关系的 `usage_modes`。
3. 新增 `application_listings`、`application_releases`、`application_installations`，不使用数据库外键。
4. 已有应用任务的渠道回填为 `direct`。普通任务继续保持空渠道。
5. 旧独立副本不可靠推断来源，不补造更新关系，继续作为独立应用使用。

迁移 `20260916040000_add_application_version_labels` 新增 `application_versions.version_label`，将历史整数版本 `N` 回填为 `N.0.0`。保留原版本 ID、内容、递增序号及安装和审批关联，不删除历史数据。对外 API 的 `version_number` 等字段改为语义化版本字符串，前后端需同步部署。独立 `POST /applications/:id/publish` 与旧 `POST /applications/:id/grants` 已移除，组织内共享通过 `POST /applications/:id/share` 原子保存版本和共享关系；上架申请直接提交版本号与使用说明，不再要求先获取发布版本 ID。

由于移除了旧字段，部署应暂停旧版本 API 和执行进程，完成数据库备份与正式迁移，再以同一代码版本生成 Prisma 客户端、构建并启动服务。不得让旧 API 在移除字段后继续处理请求。不要使用 `db push`、重置数据库或重新导入历史应用代替迁移。

## 验证

- 单元测试：分发权限、版本选择、安装资源、三方合并、审批权限、API 输入验证，以及中英文页面操作。
- `pnpm --filter @linksense/api exec tsx test/integration/application-distribution-postgres.ts`：自动创建临时 PostgreSQL，先迁移至旧结构并写入代表性历史数据，再运行本次迁移；验证真实服务及 HTTP 接口、普通/交互式安装更新、凭据绑定保留、审批版本隔离和撤销。
- `pnpm --filter @linksense/api exec tsx test/integration/user-project-runtime-postgres.ts`：覆盖已有项目、历史应用发布版本、任务和外部访问身份的整体升级回归。

集成测试不读取应用 `.env` 数据库地址，结束后清理其临时容器与目录。`--serve` 为本地浏览器验证保留测试 API，监听 `127.0.0.1:18400`；使用临时数据库中的身份，收到退出信号后清理。
