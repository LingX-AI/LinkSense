# 本地首字延迟复测与修复记录

测试时间：2026-09-17 13:56–14:13（Asia/Shanghai）。本记录补充[实施记录](task-response-latency-implementation-2026-09-17.md)，不替代部署环境验收。

## 结论

真实页面测试尚未达到新任务 3 秒、续聊 1 秒的端到端目标。发现三类不同问题：

1. 上一轮新增的 Worker 启动完成通知遗漏了 Controller 转发路由，真实容器拓扑返回 404。这是本次已修复的代码缺陷。
2. 正常完成的三个页面样本中，主回答上游请求等待首段非空文字花费 13.39–24.40 秒，远大于前端显示耗时。优化启动不能消除这部分等待。
3. 三次续聊测试遭遇本地 API 进程退出、事件积压；容器仍存活，但 HTTP 服务不可用。Docker `OOMKilled=true` 和容器 cgroup `memory.events` 中的 `oom_kill=1` 确认内存不足终止。第一轮中断还叠加 Controller 源码热更新后的 Worker readiness probe 退出。这些失败不能归入上游接口豁免。

用户选择保留当前 Docker 配置，先交付结果与代码修复。没有调整 Docker 内存、重启 Docker Desktop、修改模型/推理强度或部署远端环境。

## 环境和口径

- 分支 `develop`，基础提交 `5d619e02e5e6865a477b4d9a3a131fba5279b58f`，叠加当前未提交工作区；工作区有其他任务的并行改动。
- 本地 Web 为 Vite 开发服务 `localhost:18173`；API、Controller 和持久化 Worker 使用实际 Docker 拓扑。
- Docker：8 个 CPU，`MemTotal=4108632064` 字节，约 3.83 GiB；宿主机内存 16 GiB。项目 [README](../../README.md) 要求 Core 至少 8 GiB、Full 至少 16 GiB。
- Worker 镜像 `linksense-runner-worker:oss-local`，测试时镜像 ID 为 `sha256:f9670ac0b8aab5589c35936fffd48dce4a5ad281e4ff73dade850140e1c5f7a4`。
- 实际业务 turn 全部使用 `Qwen3.8-27B`、`low`，渠道 revision 为 108，协议 `responses_tool_compat`。首次页面显示的模型选择存在配置更新前的状态，归因以持久化 turn 的实际模型为准，没有人为切换模型。
- 使用 ego-browser 在登录页面真实填写并点击发送；提示词只要求回复“收到”、不调用工具。脚本共提交 2 个新任务、4 次续聊。环境同时存在其他请求，不是隔离压力测试。
- 页面首字是 `linksense:ui_first_text_commit`，起点为发送 mutation 开始，新任务包含创建耗时；它测 React 首次提交非空 AI 文字，不等同显示器绘制完成。三个正常样本从点击到计时起点分别相差 4.7、2.9、0.9 ms。
- 上游时间是网关在原始 HTTP 响应流中观察到的首段非空回答文字，观察点在协议转换之前。响应头、空白 delta、推理状态以及 `memoryOperation=extract/consolidate` 请求不计作主回答首字。

## 已交付修复

在 `apps/runner/src/controller/server.ts` 的显式回调转发清单中补上 `/internal/runner/start-settled`。继续使用既有 owner/service-session 鉴权和 API 转发机制，没有通配路由、绕过授权或额外提交 Codex turn。

新增回归覆盖：

- 原路由缺失时有效 Worker 回调返回 404，修复后返回 200。
- 伪造其他 owner 凭据仍返回 401，且不访问 API。
- 转发目标正确；业务启动操作 ID、runtime generation、service session 和 API 回执保持一致。
- Worker 侧 scoped token 在 Controller 边界按原设计转换，不将其作为 API 全局凭据使用。

实际运行验证中，修复后的新任务与续聊回调均到达 API，`start_projection` 成功，回调请求分别约 80.8、61.3 ms 完成。此前同一路径返回 404，只能等待持久化恢复轮询。该修复消除了通知链路遗漏，不能解决模型本身的首字等待或 Docker 内存不足。

## 内存问题的边界

API 子进程的一次存活快照 RSS 约 732 MiB，另有开发 watcher、文档转换进程；其他容器也共享仅约 3.83 GiB 的 Docker VM。退出后的快照中 API 主进程消失，watcher 仍活着；因此 Compose 的 `restart: unless-stopped` 没有自动恢复应用监听端口，健康检查转为 unhealthy，Worker 的持久化事件只能退避重试。

这证明本地存在实际资源不足和开发模式子进程退出后未恢复的问题；尚未证明某个模块内存泄漏，也不能把每次退出都归咎于源码热更新。部署环境是否存在相同内存压力、进程托管问题，尚未测量。

本次按需重启失效的本地 API/Controller 以恢复事件交付；没有关闭其他用户 Worker。两条本轮新建测试任务在所有 turn 完成后通过正常业务删除接口清理，均返回 204，Worker 收到对应 runtime 清理请求。结束前 API、Controller、Web 健康检查恢复正常；保留原资源配置意味着 OOM 仍可能复发。
