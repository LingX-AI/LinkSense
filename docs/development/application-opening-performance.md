# 应用打开流程提速

## 范围

优化“继续开发”和“使用”的打开路径，复用现有 TanStack Query、任务创建服务和请求耗时日志。不修改数据库、对外接口、安装版本策略或运行环境的隔离规则。

## 已移除的等待和重复工作

- 点击“继续开发”“开发新版本”“创建交互式应用”或“使用”后，立即离开列表，显示通用 Loading，准备工作在该页面显示期间完成。自身应用、组织共享应用和应用中心使用同一打开流程，仍使用原有渠道和安装版本。
- 使用现有 TanStack Query mutation cache 保存本次打开请求及结果，按用户和操作 ID 隔离。请求只从点击操作触发，目标页面只观察结果；接口返回后再替换为真实任务地址。任务列表和应用列表后台刷新，不阻塞跳转。
- 目标页面的代码加载、任务数据加载和交互式应用 iframe 加载期间继续显示通用 Loading；iframe 实际触发加载完成后移除覆盖，避免请求结束到页面渲染之间的空白。
- 将打开接口返回的完整草稿写入按用户和任务隔离的开发查询缓存。目标页面可以立即显示开发布局，遵循现有查询缓存有效期；源码同步仍独立进行，不把缓存当作源码或权限的最终依据。
- 恢复已有开发任务时复用本次请求已验证归属的草稿和任务记录，正常路径由两次草稿读取、两次任务读取减少为各一次。任务已删除时仍重建开发对话；归档恢复和标题同步继续生效。
- 应用任务创建路由只传递应用 ID 和渠道。任务服务在用户运行租约内解析一次当前已安装配置，并将本次请求的结果用于创建任务，避免路由与任务服务各解析一次。
- 新任务的名称、版本和交互式应用包来自同一份解析结果。该结果仅在当前创建调用内复用，不跨请求、跨任务或跨轮次缓存。

## 保留的边界

- 权限、应用状态、安装版本和资源可用性仍由服务端检查；失败时不准备目录、不创建任务。
- 目录准备、运行资源清理、正式与调试环境隔离，以及安装更新期间的互斥规则保持现状。
- 创建任务所需的目录和持久化任务标识仍在接口返回前完成。冷环境不再为此启动工作容器；首次执行或原有预热流程仍按原生规则启动容器。没有新增预热进程、共享缓存或额外环境。
- 打开页面不因挂载、Strict Mode、重新渲染或浏览器刷新自动重新发起创建请求；重复点击受同步保护。页面离开后不会由请求完成回调强行跳转，切换账号后不可读取前一账号的操作结果。
- 失败在当前页面显示并提供显式重试、返回应用列表。完整刷新导致内存操作记录丢失时提示返回列表，不猜测上次创建是否成功，也不自动重放请求。
- 无持久化数据格式变化；已有应用和任务无需重新安装或迁移。

## 耗时观测

复用请求上下文中的结构化日志，新增以下阶段：

| 阶段 | 含义 |
| --- | --- |
| `application_runtime_resolution` | 应用任务创建时解析权限、安装版本和资源 |
| `application_home_prepare` | 准备运行主目录 |
| `conversation_storage_prepare` | 运行服务准备任务存储 |
| `application_development_open` | 恢复开发任务或从已发布应用进入开发 |

日志沿用请求关联标识、阶段耗时和结果，不记录应用源码、提示词或凭据。这些阶段可能包含嵌套操作，不能直接相加。优化效果先用阻塞等待及调用次数验证；真实打开耗时须在实际环境按相同应用和冷热状态对比，不能从单元测试耗时推算。

2026-09-19 本地日志小样本观测：运行配置解析 2 次，中位数约 32 ms；主目录准备 4 次，中位数约 12 ms；任务存储准备 4 次，中位数约 2.05 s、最大约 4.28 s。任务存储准备会经 runner controller 获取应用工作容器，冷启动时需要启动容器并等待就绪。该采样不足以代表稳定的性能分位数，但说明仅优化配置查询无法消除所有等待，因此将立即导航和实际准备耗时分开处理。

## 回归覆盖

- 接口尚未返回时已完成跳转并显示通用 Loading，列表刷新不阻塞最终任务显示；中文、英文及缺失语言回退。
- 正式使用保留应用渠道及普通/交互式路由差异；错误显式重试、快速重复点击、离开页面、Strict Mode、刷新、账号切换均不自动重放或错误跳转。
- 目标页代码和数据加载有通用 Loading，交互式预览持续显示通用 Loading至 iframe 加载完成。
- 目标开发页面直接使用打开结果，缓存按用户隔离。
- 继续开发保留原有对话、草稿和预览，不重建未变化的环境；归属错误仍拒绝。
- 任务创建只解析一次配置，名称和包版本一致；权限及资源校验失败不分配环境。
- 已有应用、组织共享、应用中心安装与历史数据通过现有单元及隔离 PostgreSQL 集成测试验证。

## 全链路优化（2026-09-19）

实际检查了列表点击、目标路由代码加载、任务创建、应用配置解析、目录与 worker 准备、开发预览同步、运行票据、iframe 资源和后续执行链路。

| 环节 | 原先等待 | 本次处理 |
| --- | --- | --- |
| 页面代码 | 打开接口完成后才加载目标路由模块 | 点击时与 API 请求并行加载，复用浏览器模块缓存和 React.lazy 入口 |
| 任务创建 | 存储准备必经获取工作容器、容器启动和健康检查 | 已确认无容器时直接准备工作目录及控制记录；存在容器时保留原 worker 检查 |
| 已有 worker 的存储接口 | 调用执行工具初始化入口后准备文件 | 只准备存储；工具仍由 worker 启动、预热和执行入口初始化（原初始化已有成功缓存，不将其误算为反复初始化的耗时） |
| 预览数据 | 任务详情 → 应用详情 → 运行票据 → iframe | 任务详情和应用详情并行；二者校验成功后才获取票据 |
| 开发同步 | 首次未变化的同步也使任务、预览、列表缓存失效 | 用打开时的数据初始化比对记录，仅名称、预览任务或源码版本变化时刷新 |
| 静态资源 | 按运行票据获取 HTML 和资源 | 保持现有 HTML no-store、其他资源 private immutable 缓存和服务端授权，不绕过安装版本检查 |

### 运行边界

冷环境仍复用同一份目录规范、UUID generation 的原子创建与校验逻辑；Linux 上控制文件属于 supervisor，0700 控制目录和 0600 文件保持不变。已有 generation 被保留，损坏的 generation 被拒绝；不通过伪造任务状态来提前返回。个人、正式应用和调试应用仍按现有环境标识隔离。

已存在、正在运行或状态不能确认的 worker 不走存储准备捷径。后续真正执行任务仍通过原有 worker / Codex 生命周期和资源授权；本次不改变原生重试、运行并发或回收策略。旧任务文件不会因存储准备被清空，已有数据格式无需迁移。

### 测量结果及局限

优化前本地运行日志的另一组样本：配置解析 5 次，中位数 10.9 ms；主目录准备 7 次，中位数 12.3 ms；任务存储准备 7 次，中位数 1,897.1 ms、最大 4,642.5 ms；继续开发 3 次中位数 24.6 ms、最大 4,530.9 ms。说明冷环境准备是主要等待，已有开发会话的恢复本身可以很快。

最终隔离 Docker 实测（避开并行构建和单元测试）：

| 样本 | 无 worker 时准备任务存储 | 随后启动 worker 并验证同一任务 | 已运行 worker 中准备新任务 |
| --- | ---: | ---: | ---: |
| 1 | 44 ms | 3,662 ms | 15 ms |
| 2 | 48 ms | 3,448 ms | 16 ms |
| 3 | 48 ms | 4,166 ms | 48 ms |

三次存储准备都没有创建工作容器，随后真实 worker 采用相同 generation，已有文件也保留。这段容器启动现在不再阻塞页面打开。此前并行构建期间的同一测试测得存储准备 74–366 ms，说明环境负载也会显著影响数值。生产日志与隔离测试不是同一组应用，不能据此宣称固定的整页提速百分比或性能分位数。首次实际执行任务仍可能承担冷启动成本。

没有运行浏览器自动验证；以上为服务阶段计时和组件测试，不等同于真实浏览器首屏或 iframe 绘制时间。

### 验证

- runner 全量单元测试：846 通过；1 个已有 Linux 专用条件用例在 macOS 跳过，对应权限场景由 Docker 实测覆盖。
- API 任务创建、开发工程和应用路由相关测试：367 项通过。Runner 存储接口解耦后的执行与归属相关测试另外重跑 202 项通过。
- Docker 隔离测试：冷准备不启动 worker、真实 supervisor 采用同一 generation、文件持久化、正式/独立环境隔离、任务清理保留共享文件、环境删除不影响其他环境，均通过。
- 前端相关组件测试 181 项、application 路由测试 253 项通过，覆盖请求未结束时启动模块预加载、详情并行但票据仍等待授权检查、未变化的同步不触发重复刷新，以及真实变化后的刷新。一次并行构建期间的旧用例发生 5 秒超时，避开负载后整组重跑通过，没有修改断言或放宽超时。
- 验证命令：`pnpm --filter @linksense/runner test`；`LINKSENSE_TEST_WORKER_BASE_IMAGE=linksense-runner-worker:oss-local pnpm test:runtime:docker-shared-home`；前端相关 Vitest、application 项目、typecheck/build 和 lint。
- 本机默认 `linksense-runner-worker:local` 镜像依赖旧于当前源码，Docker 验证显式使用当前开发栈的 `oss-local` 基础镜像；无需修改生产依赖或运行中的用户容器。

前端与 runner 的类型检查、生产构建和 lint 均完成；前端保留原有 TanStack Virtual 编译提示及大 chunk 构建提示，未新增 lint 错误。
