# 跨任务引用与自动化 IM 通知

本次交付先实现 DeerFlow 去重复核中的两项优先功能：当前消息引用其他任务，以及自动化运行完成后的主动 IM 通知。条件自停、每次新会话、浏览器面板和记忆编辑不在本次实现范围内。

## 操作入口

1. 普通聊天输入框输入 `@`，继续输入任务名筛选候选，用方向键选择、Enter 确认或直接点击；Esc 取消并保留原文字。选中后转为引用标签，焦点和光标位置保留在输入框，最多引用三个本人任务。邮箱地址和 URL 中的 `@` 不触发。也可从「添加 → 引用其他任务」进入原有多选面板，切换已归档任务及继续加载。发送后消息显示来源链接；运行中带引用的新消息进入后续请求队列。
2. 新建或编辑自动化，在「结果通知发送到」选择已验证的 IM 会话。默认保留站内和浏览器通知。候选来自现有个人飞书或机器人渠道的会话绑定，不接受任意外部群 ID。飞书个人助手仍仅支持本人私聊；其他机器人渠道的群聊继续受原有发送者和群聊授权限制。

新建任务、发送失败和刷新页面时，引用选择随本地草稿保存。旁聊和应用托管会话保持原有交互；Goal 提交不附带跨任务引用。

当前企业微信和 Teams 通知仅暴露已允许群聊的渠道绑定；它们旧的加密回复上下文不能可靠区分私聊与群聊，不能因此放宽通知权限。钉钉使用已有的会话类型，个人飞书使用已验证的本人私聊。此限制不改变任何已有渠道收信/回复行为。

## 授权与数据范围

跨任务引用沿用现有消息元数据、持久提交与 MCP 链路，没有新建会话执行引擎。输入元数据只传明确选择的任务 ID；服务端校验 owner 和来源类型，保存可信的消息展示记录。排队请求另保存内部选择事件，启动时再次验证，不能通过伪造消息正文得到授权。

`read_referenced_conversation` 只接受来源 ID、游标与偏移。Runner 绑定当前活动任务和投影轮次；API 每次检查当前轮的可信选择、账号状态及来源 owner。来源在读取期间被删除或原生线程改变时拒绝返回结果。来源没有被本轮选中时，即使 ID 在提示或旧历史里出现也不可读。

返回的是来源当前原生线程中可见的 user/assistant 文本。Office/旁聊等内部封装转为用户可见的提问，隐藏的计划 Stop Hook 消息会过滤；不开放附件、工具日志或推理。每页最多 20 条、共 16,000 字符，截断使用 `next_cursor` 与 `next_offset` 继续读取，不把整段历史预先复制到新提示中。

## 通知执行与兼容性

自动化的 `notification_target_json` 为可空配置。旧记录和未传新字段的请求均保持不主动发送 IM。日程、执行目标和 Codex turn 语义不变。

选择了接收位置的运行在派发事务中创建一条唯一通知记录，冻结这次接收位置。通知记录等待原执行结果，复用已有最终答复读取和渠道发送方法，发送本地化标题、有限结果摘要与回 LinkSense 查看完整结果的提示。通知重试不会重新提交 AI 任务。

通知由现有渠道运行时的 `DurableWorkDispatcher` 扫描；数据库的状态、处理令牌和过期时间负责跨进程抢占。机器人通知只由持有相应在线连接的 API 实例处理，个人飞书复用 REST 发送。发送前重查账号、任务、目标和投递令牌。关闭或更换目标会取消等待和重试的通知，恢复配置不会复活已取消记录；已开始的外部请求无法撤回。

发送异常最多尝试五次，持久记录稳定错误码。飞书使用通知 ID 作为上游幂等键；其他渠道在「平台已接收，但本地未确认」的故障窗口仍可能重复送达，不能承诺 exactly-once。通知只包含结果摘要，不自动分发完整附件。

运行失败或被中断时直接读取原生 turn 的终态，不依赖仅在成功后写入的自动化完成时间。排队运行用原始幂等键找到实际 turn 后读取摘要；只有文件、没有最终文本的成功运行仍可发送完成提示。投递取得渠道发送锁后，再检查通知处理令牌、账号与任务，防止等待锁时被撤销的通知继续送出。

更新部署时需先应用 `20261022090000_add_automation_notifications`，然后更新 API、Runner 和 Web。迁移只增加可空列与新表，不重写旧自动化，不修改已发布迁移。Runner 下一次配置内置 MCP 时会刷新新服务的环境变量列表，保留用户配置。

## 2026-10-22 整体审查修复

以 `39d0a5984d07aab3d061bdc162e399949d6d229c` 为基线审查全部未提交改动，分别核对工程规范和已确认需求。以下六项均先用回归测试复现，再修复：

1. 原生执行失败或中断后，通知一直等待自动化完成时间，无法发出失败提示。
2. 取得渠道发送锁之前的授权检查存在空隙，等待期间撤销的通知仍可能发送。
3. 排队运行保留空的 `turnId`，导致完成通知缺少已有的结果摘要。
4. 历史消息可达一千万字符，但续读偏移上限只有一百万，后续分页被自身输入校验拒绝。
5. 直接调用 pending steer 接口会把结构化引用封装注入当前 turn；现在与界面保持一致，保留在队列中。
6. 提交等待期间重建乐观消息对象时丢失引用展示元数据；现在提交完成前仍显示来源链接。

兼容性核对覆盖旧自动化的缺失/空通知配置、现有普通消息和 Office/旁聊交互，以及超过一百万字符的原生历史。未修改原生执行重试或生命周期策略；部署仍需按上述迁移顺序进行。
