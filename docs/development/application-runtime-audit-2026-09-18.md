# 应用运行环境全链路审查（2026-09-18）

## 审查范围与结论

本报告审查当前 `develop` 工作区，包括暂停前已写入、尚未完成验收的应用更新改动。工作区存在大量其他未提交变更；本次不修改业务实现、不执行数据库迁移、不搬迁或删除用户环境、不重启正式服务。只读盘点针对本机开发数据库及数据目录，不代表远端生产环境。

当前已具备发布快照、分渠道授权、任务启动检查、原生会话恢复、空闲容器回收和明确删除后的环境回收链路。但“应用版本选对”与“实际执行文件不被其他版本修改”仍是两件事：数据库分渠道版本测试通过，真实 Codex 原生测试已复现旧进程的 Skill 文件被新版覆盖。

主要结论：

1. 普通应用、交互式应用、创建者、直接共享用户和安装副本采用不同的环境选择规则；历史任务不会自动迁移到新规则。
2. 同一执行用户、同一应用的任务共用 HOME、CODEX_HOME 和工作目录；环境身份不包含发布渠道或版本。
3. 下一轮重新解析当前入口的应用配置，但继续使用原任务目录与原生会话。当前实现没有做到可靠的并发多版本执行隔离。
4. 清理机制较好地保护了用户文件，但自动回收覆盖不完整。任务完成、授权撤销、会话过期、应用删除，都不等于删除持久化环境。
5. 暂停前的改动不能认定为已完成：原生并发回归失败，API 类型检查也存在未完成测试代码导致的失败。

## 一、实际上存在的几层“环境”

| 层次 | 存储/对象 | 当前边界 |
| --- | --- | --- |
| 应用当前配置 | `Application` 与资源绑定表 | 创建者正在编辑或已导入的配置；可以变化 |
| 分发版本 | `ApplicationVersion` | 发布时冻结应用指令、模型设置、Skill/插件文件及知识库、MCP 的 ID |
| 渠道版本入口 | `publishedVersionId`、应用中心审核通过的 release | 组织直接共享与应用中心分别推进版本 |
| 交互式页面包 | `InteractiveApplicationPackage`、资产表、MinIO | HTML/JS/CSS 等通过运行票据在浏览器中加载；不是整个 Worker 环境的快照 |
| 持久化运行目录 | 用户 HOME、`.codex`、`workspace`、增量依赖 | 个人级，或“执行用户 + 应用 ID”级；通常跨任务、跨版本复用 |
| 运行中的执行单元 | Worker 容器、任务的 app-server、原生 thread/turn | 容器可回收重建，任务有独立会话，但可共用上面的文件目录 |
| 启动及恢复记录 | `ConversationTurnStartIntent`、`ConversationTurn`、运行代次 | 保存资源和启动信息，支持幂等接纳、恢复与原生终态确认 |

当前没有一个统一的持久化“应用环境版本”对象，将页面包、发布版本、能力文件摘要、CODEX_HOME、Worker 镜像、依赖环境和所有引用者绑定起来。

核心路径来自 `packages/shared/src/runtime-workspace.ts:28`：

```text
个人：users/<执行用户>/home
应用：users/<执行用户>/services/<应用 ID>/home

应用 HOME 内：
  workspace/                 多个任务共享的工作文件
  .codex/                    原生历史、配置和插件缓存
  .agents/current/           当前托管能力快照的入口

任务控制目录：按任务单独存放
```

不同执行用户不会仅因为使用同一个应用而共用 HOME。采用应用目录的新任务，不同应用也分开。个人任务、未发布普通应用及未发布的安装副本则可以共用个人 HOME；项目只进一步决定工作目录，不隔离整个 CODEX_HOME。

## 二、从创建到使用：各入口实际策略

创建普通应用主要保存配置及资源引用；导入交互式应用还保存页面包与资源声明。资源声明必须解析成创建者有权使用的实际资源，声明本身不授予权限。完整 Worker 环境并非在每次保存应用或导入 ZIP 时复制一份，而是在预热/任务启动时准备、按需启动。

| 使用入口 | 当前配置来源 | 新任务目录 | 更新行为 |
| --- | --- | --- | --- |
| 创建者使用未发布普通应用 | 当前应用配置 | 个人 HOME / 项目工作目录 | 下一轮读当前配置，能力准备走个人资源范围 |
| 创建者使用已发布普通应用 | 当前直接共享发布快照 | 用户 + 应用 ID | 保存编辑不等于推进发布快照；需执行发布/共享更新 |
| 创建者从“我的应用”使用交互式应用 | 当前页面包和当前资源绑定 | 用户 + 应用 ID | 暂停前新增的特殊处理：忽略直接共享发布指针，使用当前配置 |
| 组织内被共享用户直接使用 | 创建者当前直接共享发布快照 | 执行用户 + 原应用 ID | 新任务、旧任务下一轮解析最新共享版本 |
| 应用中心直接使用 | 当前审核通过的 release 对应快照 | 执行用户 + 原应用 ID | 只有新 release 审核通过才升级；不会跟随组织共享自动更新 |
| 安装普通应用为副本 | 自己的 Application 与复制的能力资源 | 未发布时使用个人 HOME | 独立维护；更新需要用户主动应用，保留本地修改及个人凭据 |
| 安装交互式应用为分发副本 | 当前分发策略不允许 | 不适用 | 交互式应用通过 service 直接使用；不要与开发界面的“发布到我的应用”混同 |
| 开发预览 / 试运行 | 开发预览应用与预览页面包 | 用户 + 预览应用 ID | 与正式应用的 ID 和试运行记录分开 |
| 外部嵌入访问 | 应用发布配置，受外部访问权限约束 | 执行身份 + 应用 ID | 新匿名身份会分配独立执行身份，不直接等同于登录用户 |

代码入口：

- `apps/api/src/modules/applications/service.ts:127`：创建者交互式应用的特殊版本选择。
- `apps/api/src/modules/applications/service.ts:1434`：运行配置解析。
- `apps/api/src/modules/applications/distribution-policy.ts`：direct/center、service/install 授权。
- `apps/api/src/modules/conversations/service.ts:7056`：新任务运行位置选择。
- `apps/api/src/modules/application-embed/service.ts:1087`：匿名运行身份与任务创建。

### 发布不是单一动作

当前至少存在三个独立概念：交互式包自身版本、应用分发快照版本、开发预览修订号。开发预览同步不会直接改正式应用；开发界面发布会导入/更新正式应用；组织共享和应用中心分别有发布指针。

暂停前改动已经在代码中实现：对于已经有直接共享发布版本的正式交互式应用，更新页面包时在同一事务中更新包和资源绑定、创建发布快照、推进直接共享指针。缺失依赖会拒绝整个更新。应用中心已审核 release 不跟着变化。

这条数据库链路的集成测试通过，但不代表并发运行环境已隔离。相关实现位于 `apps/api/src/modules/applications/service.ts:661`，中心提交/审核位于 `center-service.ts`、`distribution-repository.ts`。

### 冻结和实时依赖的边界

发布时真正复制并冻结了 Skill/插件文件，保存内容摘要。知识库和独立 MCP 仅记录所选资源 ID；知识库内容、MCP 服务及其配置、创建者凭据和资源可用状态仍有实时性。资源被禁用、授权被撤销或凭据失效，可能使已发布应用不能继续启动或调用对应服务。

因此“应用中心仍是审核通过的旧版本”不等于所有外部依赖永远不变。组织直接使用借用创建者授权的应用资源；安装副本则需使用安装者自己的凭据，并按要求重新配置知识库/MCP，不复制创建者秘密。

依据：`publication-service.ts:94`、`services.ts:1025`、`services.ts:1112`、`services.ts:1394`。

## 三、新任务、旧任务与运行中的任务

### 一轮执行的实际链路

1. 根据用户身份、应用 ID、任务保存的 direct/center 渠道，检查当前访问权限并解析版本。
2. 准备对应能力、凭据、MCP、模型与知识库范围；校验缺失、停用和越权情况。
3. API 生成托管能力快照，更新环境内的当前快照入口。
4. 记录启动意图、资源代次和幂等信息，保护原生启动读取配置的阶段。
5. Controller 按存储环境选择/创建 Worker，Runner 校验摘要，并通过原生插件机制准备能力。
6. 创建或恢复该任务的原生 thread，提交一次原生 turn；不会因为流重连再启动一轮。
7. 接纳成功后记录该轮资源信息，并更新 Conversation 上最近使用的应用版本和页面包。

`application_version_id` 当前表示最近一次接纳执行的版本，不是任务创建时永久锁定的版本。

### 当前策略矩阵

| 场景 | 当前行为 | 限制 |
| --- | --- | --- |
| 发布后创建新任务 | 重新解析相应渠道的当前版本 | 仍会复用该用户、该应用既有 HOME |
| 旧任务完成后继续追问 | 重新解析渠道当前版本，保留文件与原生会话 | 在原目录刷新资源，没有迁入独立的版本环境 |
| 旧任务仍在运行 | 不主动中断、不重发；保留原进程和已接纳配置 | 共享磁盘上的能力文件可能被新任务改写，已复现 |
| 启动准备后恰好再次发布 | 允许本次已经准备好的版本完成接纳 | 下一次执行再取最新版本，避免把并发发布误当启动失败 |
| Worker 空闲回收后再执行 | 重建执行进程，复用持久化 HOME 和会话状态 | 旧缓存、用户依赖和文件也继续存在 |
| 故障后读取已终结原生任务 | 可用原生只读查询确认终态 | 不能确认终态或仍继续的 Goal，不猜测完成、不额外重放 |
| 访问权限被撤销 / 应用停用 | 后续使用重新校验并拒绝；部分资源调用会即时重新授权 | 不等于立即删除文件，也不等于取消所有已发出的外部请求 |

依据：`conversations/service.ts:796`、`:7540`、`:7744`、`:9181`，`applications/runtime-version.ts`，`process-pool.ts:5041`。

### 交互式页面另有一条版本链

正常前端根据任务已接纳的 `package_id` 请求运行票据；票据指向具体页面包。应用提交下一轮后刷新任务详情，再取得最新接纳的页面包。自定义事件按该任务当前接纳包的 manifest 校验。

这里不能只看卡片显示的应用版本：页面资产、后端应用指令、Skill 文件都需要对齐。当前有两个需处理/验证的边界：

- 票据接口允许只传 `conversation_id` 而不传 `package_id`。这种情况下没有默认采用任务的包，而是再次解析当前应用包。正常前端明确传包 ID，因此该问题目前主要在接口边界。
- 用户停留在旧页面时提交，新一轮后端会选择新版本，随后页面才刷新。若新版改变了输入格式或事件协议，旧页面产生的请求是否能直接用于新版本，没有完整端到端验证。

依据：`interactive-application-page.tsx:143`、`interactive-application-submission.ts:139`、`applications/service.ts:852`、`events/service.ts:185`。

## 四、环境回收实际覆盖了什么

| 触发条件 | 当前回收范围 | 会保留什么 |
| --- | --- | --- |
| 一轮任务完成 | 结束对应轮次；原生进程另有空闲关闭机制 | HOME、文件、依赖、会话历史 |
| Worker 空闲 | 默认 900 秒阈值且无用户进程、运行轮次、app-server 和在途请求时释放容器 | 持久化 HOME，不因容器释放删除磁盘数据 |
| 归档任务 | 改变可见/归档状态 | 整个环境引用仍存在 |
| 明确删除个人任务 | 删除业务记录、任务控制数据；保留已登记成果引用 | 共享个人 HOME、项目文件 |
| 删除应用环境中的一个任务 | 写清理 outbox，删除该任务控制数据 | 若其他任务或分叉仍引用，则保留整个 HOME |
| 明确删除应用环境最后一个任务 | 成果已保存且确认无活动挂载后，后台删除整个环境 | 已保留的对象存储成果 |
| 创建任务失败的补偿 | 回收失败任务的控制记录 | 不授予整环境删除许可 |
| 删除正式应用 | 软删除、撤销分发/外部访问、处理其开发预览 | 历史正式任务及其 HOME、历史发布包仍可能存在 |
| 删除开发对话 | 解除开发工程与对话的关联 | 开发工程、源码、预览及试运行记录仍归应用所有 |
| 明确删除草稿/开发工程 | 无运行试验时删除私有试运行任务，进入相同 outbox 清理 | 源开发对话和用户源码文件保留 |
| 外部会话过期 / 退出登录 | 令牌和会话失效 | 历史任务和执行身份 HOME 不自动删除 |
| 取消组织共享 / 应用中心下架 | 撤销后续入口权限 | 不自动删除已有历史任务及环境 |

整环境删除的保护链路已经比较完整：数据库事务保存成果并写 outbox；后台取得用户生命周期锁，重新检查全部任务引用；Controller 取得环境锁，关闭/释放相关运行实例，检查其他容器挂载及路径安全，最后删除并验证目录消失。失败有持久化状态、租约、重试和人工重试入口，默认最多 8 次尝试；不把不确定结果当作删除成功。

依据：`conversations/deletion.ts:23`、`adapters/jobs.ts:668`、`controller/worker-manager.ts:398`、`:584`、`runtime-cleanup.ts`。

### 仍然缺少的回收闭环

- 未发现历史 `ApplicationVersion`、发布能力文件副本、交互式包和页面资产的通用引用回收器。
- 未发现过期交互式运行票据和过期外部运行身份对应任务/HOME 的完整保留期与回收流程。
- 托管能力快照只在生成新快照时尝试裁剪，保留当前入口和少量旧快照；环境有运行任务时跳过。若此后再无新快照生成，跳过的积压不保证及时清理。
- 原生插件缓存、uv/pnpm 缓存、用户安装依赖及原生历史没有统一自动容量回收规则。不能因为目录名含 cache 就直接删除。
- 任务创建失败等路径可能留下没有任务引用的应用环境，但现有保护刻意不授予整环境删除许可，需要专门的失败资源识别与回收规则。本机本次未发现这样的目录。
- 开发工程的孤立试运行恢复已有定向处理，不等于整个系统的孤立应用环境扫描器。

“仍有引用”不一定意味着用户仍能使用。例如软删除应用的历史任务、过期匿名会话的任务继续引用环境，现有最后引用删除规则不会回收它们。这些数据也不应未经保留政策确认就当作垃圾删除。

## 五、发现的问题与证据等级

### [MAJOR] 1. 旧执行进程的 Skill 文件会被新版覆盖——已复现

同一 HOME 内通过原生 `plugin add` 刷新同名、同 manifest 版本插件时，缓存路径复用 `.codex/plugins/cache/<市场>/<插件>/<版本>`。旧进程没有退出，但其已发现的 Skill 路径中的内容改变。

真实 Codex 0.154.0 测试使用两个 app-server、同一个临时 HOME；保持旧客户端的原生 MCP 调用在途，发布新 Skill 内容并由新客户端发现。新客户端正确读到新内容，但旧客户端原先 Skill 路径也已变为新内容，断言失败：

```text
an active client's Skill path must retain its admitted contents
```

这证明保留旧进程不足以实现“正在运行的旧任务不受应用更新影响”。测试不调用外部模型、不操作用户正式 HOME。

依据：`scripts/codex-native-plugin-refresh-smoke.mts:242`、`codex/native-plugin-manager.ts:300`、`:456`。另外，普通 Skill/插件源路径仍经 `.agents/current` 入口解析（`workspace/capability-runtime.ts:123`、`process-pool.ts:5838`），也是代码可确认的可变路径风险。

建议先确定并验证不可变执行路径及原生插件缓存隔离方案；不通过自定义重发、中断旧任务或仅延长锁时间掩盖问题。

### [MAJOR] 2. 共享入口与应用中心的不同版本共用物理环境——代码确认

环境 key 只有执行用户与应用 ID。相同用户从直接共享运行新版本、从应用中心运行仍审核锁定的旧版本时，共用托管能力当前入口、原生插件缓存、HOME 依赖和工作文件。

数据库渠道版本选择测试通过，并不能阻止两边在启动时互相刷新磁盘内容。问题 1 已证明其中的插件缓存覆盖机制。用户任务同时写同名文件或修改 Python/Node 依赖也是条件性冲突风险，本次没有额外复现该类用户脚本冲突。

建议将共享业务文件的持续性与执行代码/依赖/缓存的版本边界分开设计；具体原生会话跨环境恢复方式仍需按项目固定 Codex 版本验证。

### [MAJOR] 3. 历史任务保留旧目录，导致同一应用存在不同能力加载策略——代码与本机数据确认

每轮用任务保存的 `workspaceRelPath` 反推环境，代码不自动把旧任务迁入新目录。`applicationCapabilityScope` 仅在存在服务环境 ID 时生效；仍在个人目录中的应用任务走个人能力/MCP 范围，而不是完整应用发布范围。

本机确有 2 个交互式应用任务仍在个人目录；另有 117 个任务使用历史服务目录。现有离线应用目录归并工具只处理已在服务目录的任务，跳过个人目录，并未在本次执行。启动检查也不强制将所有历史服务目录改成规范的应用 ID 目录。

影响包括：旧、新任务加载范围不同；某些旧任务继续看到个人能力或缺失应用所需能力；同一应用目录数量不会自动收敛。不是所有历史目录都发生故障，但升级路径需要覆盖这些真实状态。

依据：`conversations/service.ts:198`、`:9181`，`operations/application-environment-conversion.ts:21`，`operations/runtime-layout-readiness.ts`。

### [MAJOR] 4. 创建者交互式使用与共享使用仍可能运行不同资源修订——代码确认、条件性影响

当前特殊分支让创建者从我的应用读取实时配置，共享用户读取发布能力副本。因此即使页面包版本相同，创建者随后修改了原始 Skill、MCP 绑定等配置，创建者测试与共享用户使用仍可能不同。

新版页面包更新并推进共享快照改善了原来的“包更新但仍选旧快照”问题，但没有建立统一的创建者正式运行规则。需要明确正式使用、开发预览和编辑未发布配置的边界。

依据：`applications/service.ts:127`、`:1468`，`services.ts:1033`。

### [MAJOR] 5. 历史发布资产及失效外部身份缺少完整保留/清理政策——代码与数据确认

现有 outbox 主要处理明确删除任务后的运行目录，而应用版本、页面包、失效票据、过期匿名身份任务等拥有独立生命周期。它们不会因为容器闲置或应用软删除自动进入同一清理流程。

本机存在已删除应用的包及失效外部身份的任务，详见下一节。这不证明所有记录都可以立即删除，而是说明产品需要区分历史保留、可恢复数据、可重建缓存和可删除孤立资源，并分别建立引用判断与保留期限。

### [MINOR] 6. 运行快照清理是机会式触发，积压不保证自动消化

能力快照裁剪只在新快照安装时执行；运行中跳过裁剪后，无独立的终态或定时补偿保证再次执行。发布源副本与原生缓存也不在此裁剪范围。

依据：`capabilities/user-home-materializer.ts:330`、`capability-snapshot-store.ts:87`，`services.ts:1664`。

### [MINOR] 7. 每轮缺少完整、持久的应用环境清单

每轮保存能力、MCP、模型和知识库范围，但 `ConversationTurn` 没有直接记录应用发布版本及页面包 ID。Conversation 上对应字段会随下一轮覆盖，启动意图又是暂态记录。已有记录能部分追溯，但不能仅靠一个清单准确回答历史轮次使用了哪套应用包、指令、缓存和运行镜像。

建议为执行与清理共同使用的审计信息定义明确边界，而不是再增设独立的自定义 Codex 生命周期。

依据：`prisma/schema.prisma:899`、`:962`、`conversations/service.ts:7540`。

### [MINOR] 8. 页面运行票据在省略包 ID 时可能偏离任务已接纳版本

接口有任务 ID 时只验证显式传入的包 ID；省略后解析最新包，未使用任务记录中的包作为默认值。标准前端显式传入包 ID，本次未将其认定为所有页面都在运行错误版本。

依据：`applications/service.ts:852`、`interactive-application-page.tsx:155`。
