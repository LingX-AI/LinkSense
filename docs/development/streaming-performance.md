# 流式事件吞吐排查与验证

本文按排查顺序保留历史结果。服务端吞吐实现与验收见「Linux 持久化与数据库吞吐优化（v23）」；2026-10-27 的页面卡顿排查与前端修复见文末。不同环境和阶段的结果不能合并推断为正式部署已解决全部问题。

记录日期：2026-09-11。模型：`deepseek-flash`，`native_responses`，`medium` 推理强度。改动前代码基准：`9711fdd`。

## 问题与定位

目标是在同一次请求上让 LinkSense 的正文接收速度跟上模型输出，避免事件积压随正文长度持续增长。供应商面板的输出 token 数可能包含推理 token，不能直接与页面可见正文的速度比较。

实际链路为：

```text
模型 → ModelGateway → Codex app-server → notificationChain
    → 持久化 outbox → Worker HTTP → Controller → API 逐事件事务
    → Redis 唤醒 → PostgreSQL 事件分页 → HTTP SSE → 前端
```

原实现每个事件单独请求 API，并等待回执、删除已确认文件、同步目录后再发送下一个事件。模型输出越快，队列越容易积压。SSE 事件历史读取还需要多次数据库往返，进一步占用处理时间。

代码检查未发现前端固定每秒输出几十个 token 的限制：已有逻辑按动画帧处理收到的全部增量，流式 Markdown 动画已关闭。本次未修改前端显示逻辑。

单独优化历史查询仍不足以解决问题：同一段真实模型事件回放中，末尾正文滞后从约 4.2 秒降到约 3.2 秒，仍然积压。因此进一步优化事件传输的固定开销。

## 实现与不变量

复用现有 Prisma、Zod、Fastify 和 outbox，不增加依赖，也不修改数据库结构。

1. 历史读取使用一个参数化 `Prisma.sql` 查询，将分支、准备阶段任务、可见事件、分页和过滤后的序列上界放在同一数据库快照内。加上原有所有权检查，空页轮询从 6 次读取降至 2 次。使用 `EXISTS`，无需加载整个分支的 turn ID 列表。PostgreSQL 单条查询的快照语义见[官方文档](https://www.postgresql.org/docs/16/transaction-iso.html)。
2. Worker 从已持久化的队列中立即取出连续完整事件，一次最多 32 条，目标请求大小 256 KiB；不等待凑满。单个已有大事件单独发送，沿用原有请求大小限制。
3. 每条事件保留原来的 `deliveryId`、内容和次序。API 依次 `await` 原有 `ingest`，每条事件仍独立执行原有事务、去重、分支检查和生命周期处理。正文、工具、审批和完成事件不需要另外分类。
4. API 只确认批次开头已按原有语义处理的连续前缀，包含原本应忽略的旧分支事件；遇到未就绪或错误立即停止，后续事件不执行。HTTP 请求断开后，在当前事件处理结束处停止。已经提交但未拿到回执的事件沿用原有 delivery ID 重试。
5. Worker 严格验证回执是原请求的连续前缀，只删除确认过的文件，再同步一次目录。乱序、缺项、陌生 ID 或多余 ID 的回执不会清理队列。每条新事件的文件与目录持久化仍在 `publish` 返回前完成。

合并的是 HTTP 往返及已确认文件的目录同步，不合并事件内容，不并行执行同一会话的事件。后端到前端的 SSE 事件契约保持原样。

测试在独立 Docker 网络、PostgreSQL 16、Redis 7.4 中运行；测试进程限制 2 CPU / 1536 MiB，数据库与 Redis 各 1 CPU / 256 MiB。使用实际 Worker 镜像中的 Codex **0.150.1** 和宿主机绑定目录保存 outbox。模型凭据仅通过受控运行时配置传入测试进程，不写入结果。

真实请求经过 ModelGateway、Codex、事件映射、持久化队列、Controller HTTP 代理、API、PostgreSQL、Redis 和 HTTP SSE。测试驱动复现 ProcessPool 的串行通知发布方式；鉴权、任务准入和准备阶段使用测试夹具。没有执行浏览器页面或生产环境测试。

在同一个单调时钟上记录每个 Codex 正文增量与对应 SSE 到达时间。吞吐比较使用相同正文的首末增量时长，同时检查每条增量的延迟，避免只看平均速度掩盖积压。

| 场景 | 模型/回放正文时长 | SSE 正文时长 | 增量延迟 P95 | 最后一段正文滞后 |
| --- | ---: | ---: | ---: | ---: |
| 修改前，真实轨迹两倍速回放 | 4.823 s | 10.266 s | 5327 ms | 5482 ms |
| 修改后，同一轨迹两倍速回放 | 4.822 s | 4.784 s | 69 ms | 14 ms |
| 修改后，真实模型请求 1 | 8.290 s | 8.270 s | 132 ms | 42 ms |

两倍速回放包含 1360 条正文增量、2363 个字符；两轮最终真实请求分别包含 1094 / 892 条正文增量、1910 / 1498 个字符。正文内容及顺序一致，增量数、持久化事件数和完成状态校验通过。两轮真实请求的单次延迟峰值分别为 202 / 251 ms。

修改后 SSE 正文吞吐约为模型的 100%，没有持续增长的末尾积压。SSE 首末时间窗口偶尔比模型窗口略短，是首段传输延迟与随后追赶造成的，不代表生成速度超过模型。

这验证了测试资源和负载下的吞吐目标。浏览器实际绘制延迟、部署网络和多任务并发未在本次性能测试中测量，不能据此承诺所有环境零延迟或不存在任何瓶颈。

## 后续 Linux 部署复测：逐事件落盘仍可形成瓶颈

2026-09-11 在用户反馈仍慢的 Linux 部署上完成复测。确认实际运行的 API、Controller 和 Worker 已包含上述批量协议，Worker 运行契约为 `shared-user-home-v22`；网关的 API 代理已关闭响应缓冲。此前的本地结果不能外推为部署环境已达标。

### 真实 deepseek-flash 请求

通过实际页面提交一个独立的纯文本任务，使用 `deepseek-flash`、`low` 推理强度。对实际 SSE 响应和正文 DOM 更新计时，并与同一次调用的原生 Codex 记录及数据库事件对齐。测试任务已归档，恢复了测试前的模型偏好。

| 测量项 | 结果 |
| --- | ---: |
| 原生记录中的模型调用耗时（含推理） | 12.387 s |
| 页面 SSE 正文首末增量时长 | 30.108 s |
| SSE 正文增量数 | 1255 |
| SSE 正文增量吞吐 | 41.7 条/s |
| 原生最终正文完成至末尾正文落库 | 约 20.7 s |
| SSE 接收到对应正文 DOM 更新的 P50 / P95 | 49 / 65 ms |
| 最后一段 SSE 接收到完整正文 DOM 更新 | 19 ms |

原生与数据库时间来自同一部署主机；SSE 与 DOM 延迟使用同一浏览器时钟计算。没有把不同主机的壁钟用于毫秒级前端延迟结论。DOM 测量不等同于 GPU 最终像素绘制时间。

正文去除空白后，SSE 拼接结果与最终 DOM 内容一致。另对两个既有任务只核对时间、字符数和摘要哈希，原生最终正文与数据库消息哈希一致，但最终正文事件分别晚约 41 s、57 s 落库。说明秒级积压已经发生在浏览器之前。

这里的“条/s”是完整事件中的正文增量数量，不等同于供应商的 token/s。模型耗时包含推理，SSE 正文窗口只包含可见正文，因此也不能直接用两者的时长比作为模型 token 吞吐比。

### 隔离掉 API 和数据库后，仍复现相同吞吐上限

在同一 Worker、同一持久卷下创建并清理独立临时目录，复用运行镜像中的 `WorkspaceManager` 和 `HttpRunnerEventSink`。依次 `await publish` 160 个完整增量事件，将 HTTP 接口替换成立即返回全部确认 ID 的测试响应，不访问 API 或数据库。

- 160 条事件完成持久化和投递清理共耗时 3.838 s，吞吐 **41.7 条/s**。
- 单次 `publish` 耗时 P50 为 23.0 ms，P95 为 27.6 ms。
- 共发送 81 个测试 HTTP 批次，平均每批约 1.98 条；模型侧的串行落盘已经限制了批次供应速度。

在同一卷另做 80 次创建临时文件、写入、同步文件、重命名、同步目录的测量：文件同步平均 7.34 ms，目录同步平均 7.31 ms，完整操作平均 16.13 ms。采用追加写时，`fsync` 与 `fdatasync` 都约 8 ms，不能假定只替换同步函数即可解决。

代码中的阻塞路径是：

```text
notificationChain 串行处理
  → await eventSink.publish
  → append 持锁写文件、fsync、rename、目录 fsync
  → 下一个原生通知才开始处理

已确认文件的清理也需要同一把锁，并执行目录 fsync。
```

因此已确认的瓶颈是**逐事件同步持久化及其锁等待对部署存储延迟过于敏感**。本次未证明物理磁盘故障，也未排除修复此瓶颈后 API 逐事件事务成为下一个限制。单个 API 实例的事件批次请求 P50 / P95 约 468 / 957 ms；这是整批请求耗时，不能当作每条事件的数据库耗时。

### 修复约束与下一次验收

本轮只定位问题并记录结果，未修改应用运行逻辑、文件系统参数、数据库持久化配置或部署镜像。不能将诊断完成表述为部署性能问题已修复。

1. 优先评估能够保留持久化保证的存储改进；在同一持久卷用上述真实 sink 基准复测，不能以顺序读写带宽或 CPU 空闲率代替同步写延迟。
2. 如果需要改为存储层的有序组提交，必须同时处理上游串行 `await publish`，否则仅增加批量 append 接口无法形成批次。所有事件保持原样和原次序，不能只移除 `await` 或提前返回成功，也不能依赖正文、工具、审批等事件类型的例外清单。
3. 存储改动需验证写入失败、同步失败、进程退出、重启恢复、确认丢失、重复投递、分支切换及完成事件顺序。通过前不能声称与现有可靠性等价。
4. 最终在同一部署上再次使用 `deepseek-flash`，按同一次请求记录原生增量、持久化、SSE 和 DOM 时序，要求正文越长时末尾滞后不持续增长，并补充并发任务验证。单独提升 sink 基准不足以证明全链路达标。

本轮执行了真实页面模型测试、同卷持久化微基准、实际 sink 隔离基准，以及部署代码和日志核对；未运行新的单元测试或构建，因为没有修改应用代码。

## Linux 持久化与数据库吞吐优化（v23）

本轮继续在上述 Linux 主机的同一 ext4 文件系统上验证。测试数据放在独立临时目录、PostgreSQL 和 Redis 容器中，未修改生产数据库、文件系统参数或正在运行的服务。

### 最终实现

1. **原生通知保持串行，待处理的相邻纯文本可以一起落盘。** 复用已安装 Codex 0.150.1 的通知契约，只有正文、计划和思考摘要的三个文本增量方法允许分组；方法、thread、turn、item 或摘要段不同就分开。准备阶段通知不分组。所有其他通知、未知通知及服务端请求都自动形成边界，无需列举一张可能漏项的「必须刷新事件清单」。没有等待凑批的定时器，也不把不同增量拼成一个事件。
2. **每个事件仍保留独立文件、原格式和 delivery ID。** 每组最多 32 条，先完成所有临时文件写入，再并发同步每个文件，随后按顺序重命名，最后同步目录。只有这些步骤全部成功才返回；写入或同步失败会等待所有在途操作结束并清理临时文件，已完成重命名的记录可按原方式恢复。没有关闭 `fsync`、提前确认成功或修改 outbox 文件结构。[Node 文件同步文档](https://nodejs.org/api/fs.html#filehandlesync)
3. **解除文件系统调用的额外串行等待。** Controller 在 Worker 的 Node 进程启动前设置 `UV_THREADPOOL_SIZE=32`，与最大落盘组一致；读取已落盘记录使用有界并发，并按原次序应用字节限制和错误处理。默认四线程不足以在该主机的同步写延迟下达到目标。这会增加 Worker 可用的 I/O 线程数，原有容器 CPU、内存限制保持不变。[Node 配置文档](https://nodejs.org/api/cli.html#uv_threadpool_sizesize)、[libuv 线程池文档](https://docs.libuv.org/en/v1.x/threadpool.html)
4. **HTTP 每批最多 64 个完整事件，API 仅将相邻同流纯文本放进一个事务。** 原有会话分支锁、事件序列锁、delivery ID 去重和回执前缀规则保持有效。事务使用参数化 `Prisma.sql` 与 PostgreSQL `jsonb_to_recordset` 批量插入，返回 ID 和数据库生成的时间；按输入恢复顺序，UUID 按 PostgreSQL 的大小写等价规则去重。用户正文只作为绑定参数传入，不拼接 SQL。其他事件继续走原有完整生命周期处理。[PostgreSQL JSON recordset 文档](https://www.postgresql.org/docs/16/functions-json.html)
5. **Redis 使用已有 ioredis pipeline。** 事务提交后按顺序发布每个原始事件，并检查整批结果。Redis 失败不确认 HTTP 回执，重试沿用原 ID，数据库不会重复插入；SSE 仍按数据库序列读取和恢复。[ioredis pipeline 文档](https://github.com/redis/ioredis#pipelining)

服务端问题请求先在通知队列中的原位置完成持久化，再异步等待用户答案；等待答案不会占住通知队列。正文、工具、审批、分支和完成事件之间的次序保持原有含义。

前端仍使用 **SSE**。`conversationStreamFrameFallbackDelayMs=50` 是页面动画帧批量更新的兜底时间，处理的是已接收的全部事件，不是每 50 ms 轮询服务器或只显示一个 token。本轮没有修改前端代码、数据库 Schema 或依赖版本。

### 为什么需要同时处理数据库

只优化 outbox 后，立即确认的模拟 HTTP 基准已达到约 395 条/s，但不代表完整链路达标。真实数据库路径最初在每秒 400 条、持续约 31 秒的回放中仍积压 3.4 秒，因此没有把短测试通过当成验收结束。

同一测试数据库中，64 条事件的事务微基准各执行 30 轮：Prisma `createManyAndReturn` 中位数约 37.0 ms，参数化 JSON recordset 插入约 14.2 ms。采用后者后，长回放的末尾积压降至约 193 ms，后半段延迟未继续增加。

| 持续 400 条/s 压力回放 | 12294 | 30.730 s | 30.553 s | 339 ms | 193 ms |

并发真实请求原生正文分别约 444 / 439 字符/s，SSE 分别约 454 / 449 字符/s。接收窗口略短来自开始传输的延迟和追赶，不代表 SSE 能加快模型生成。两路正文尾部延迟均小于 221 ms；完成事件尾部延迟分别约 300 / 382 ms。

持续压力轨迹由一段实际 deepseek-flash 的正文增量重复九次构成，只保留一次前置和结束事件，并更新最终正文，合计 21654 个字符；它是压力回放，不是一次新的模型生成，也不能用其中沿用的 token 使用量计算真实模型吞吐。该场景前段/后段正文延迟中位数为 204 / 175 ms，最大单条延迟 482 ms，完成事件滞后 415 ms。没有随持续输出增长的积压。

本轮追踪了 Worker 持久化与事件入库、详情查询、HTTP SSE、流式状态、Markdown、对话虚拟列表、交互应用开发预览和 iframe 生命周期。结论来自当前源码和本地回归测试，没有采集用户故障现场的浏览器性能轨迹、堆快照或崩溃日志，因此以下问题是已复现的性能缺陷及已识别的风险，不能归因到每一次实际崩溃。

### 已修复的问题

| 原因 | 长任务中的放大方式 | 本轮处理 |
| --- | --- | --- |
| `getNativeCodexPayload` 每次读取都执行 Zod 解析 | 同一批思考、工具及生命周期事件被状态投影、排序、活动显示等多次读取，产生重复校验和临时对象 | 按不可变 payload 对象通过 `WeakMap` 共享已校验投影；每个调用仍校验事件类型与原生方法一致，新 payload 继续完整校验；弱引用不额外保留历史对象 |
| Markdown 块上下文携带持续增长的全部回复 | 每个增量都改变 Context，绕过已有块级 memo，已完成的段落也重新解析 | 无引用时使用稳定上下文；有知识引用时保留完整来源与偏移，使引用定位继续更新 |
| SSE 在网络积压时持续同步消费 | 一个大响应块或连续已就绪的读取 Promise 可长期占用主线程；仅让出微任务无法保证输入和绘制获得执行机会 | 最多处理 64 帧或累计约 8 ms 后，通过可取消的任务边界继续；逐条保持原事件、顺序和游标提交，断开后不再派发缓冲事件。单帧解析仍不可抢占，8 ms 不是整页帧耗时的硬保证 |
| SSE 把总接收块长度当成单帧长度上限 | 大量合法小帧集中到达时可能被误判为超大帧，触发重连和重放 | 将 400 万字符限制应用于单个完整帧及未闭合的残余帧，继续拒绝真正超大的单帧 |
| 思考事件在运行期间重复保留于详情和 live state | 详情已包含正文或权威完成快照时，live state 仍保留对应事件；逐个追加还重复读取全部已有 payload | 详情刷新后释放已确认重叠部分；保留未持久化正文及其他轮次。顺序追加只检查已有事件元数据，乱序、重复和完成事件继续执行原有去重规则 |
| 切换对话的 live cache 没有容量限制 | 长时间反复切换任务会累计不活跃的流式投影 | 按最近访问保留最多 8 个对话；返回被淘汰的对话时沿用原有详情加载与 SSE 游标恢复流程，数据仍由服务端持久化 |
| HTML 预览失败后只显示错误覆盖层 | 错误 iframe 仍挂载，脚本、定时器与资源可能继续运行 | 报错或加载超时即卸载 iframe，并结束待处理截图；用户显式重试时创建新 iframe |

复用现有 React、Streamdown、Zod、TanStack Query 和原生任务调度能力，没有新增依赖。React Context 的值变化会使消费者重新渲染，`memo` 无法阻止这种更新，见 [React 官方说明](https://react.dev/reference/react/useContext#caveats)；已有 Streamdown 的[块级缓存机制](https://streamdown.ai/docs/memoization)可以直接复用。

定向测试的确定性结果：40 个已完成段落，在后续 10 次尾段更新中，修复前重新渲染 400 次，修复后为 0；尾段内容继续更新。另一项测试保留 2000 条思考增量后追加新正文，已有 payload 的额外读取次数由 2000 降至 0。它们验证重复工作减少，不等同于真实浏览器 CPU、内存或页面响应时间的测量。

### 仍需区分的风险与后续验收

**生成应用本身的同步死循环仍不能由宿主安全打断。** `interactiveApplicationRuntimeRoutes` 明确按可信应用移除沙箱策略；主页面 iframe 与运行资源同源，批注功能还会直接读取应用的 DOM。同源窗口可以共享执行线程；一个未结束的同步任务会阻塞同线程上的界面与定时器，见 [JavaScript 执行模型](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Execution_model)。因此，父页面增加心跳或超时并不构成强制终止机制。

要进一步隔离此类故障，需要将应用运行资源放到独立运行站点，严格限定消息来源、票据和权限边界，并把 DOM 批注、选区和截图转换为 iframe 内代理与宿主的消息协议。跨站 iframe 可获得支持相应站点隔离的浏览器的进程隔离，见 [Chrome Site Isolation](https://developer.chrome.com/blog/site-isolation)，但仍需逐浏览器验收，不能仅凭“跨域”宣称所有浏览器具备相同的进程和资源保证。本轮没有通过简单增加 `sandbox`、删掉批注或改写任意生成脚本来规避这些功能影响。

交互 SDK 的未完成请求和未订阅自定义事件也会随异常应用行为积累；当前协议要求缓冲事件供稍后订阅，不能静默设置截断上限。若实际堆快照证明这一类缓存占主导，需要配套设计明确的分页重放、取消和结果确认协议，尤其不能把任务提交超时误判为提交失败后自动重放。

未完成的完整正文、用户主动加载的历史和应用业务事件仍会随实际内容量增长。本轮限制的是冗余缓存和重复计算，没有给整个页面设置固定内存上限；完整内容的按需加载与回收需要分别验证读取、回放和恢复行为。

真实故障仍须区分主线程阻塞、浏览器内存不足、React 异常和后端等待。完成部署后的人工验收应使用同一长任务记录浏览器长任务、堆增长、SSE 到达与显示进度；单独复测大型 HTML、反复切换任务、预览报错、显式重试、历史加载和应用批注。后端数据库与网络等待需通过既有请求关联日志核对，不应把所有 Loading 都当作页面死锁。
