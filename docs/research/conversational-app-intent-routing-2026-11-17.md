# 对话创建应用：意图澄清、能力组合与访问地址

调研日期：2026-11-17（Asia/Shanghai）。调研时本地代码基线：`feat`，`fabff4d3`，并核对工作树；并发桌面规划不在本次范围。本文区分实施前代码事实、一手资料观察和产品建议。厂商功能按本次访问的文档描述，不能据此认定 LinkSense 已具备同等能力。地址设计是用户在调研过程中追加的范围，不预设必须使用 `/app/{slug}`。

用户随后确认按建议实施。核心实现覆盖目标式对话入口、共享意图指令、页面/数据状态、基于现有站点 ID 的稳定入口、保留旧别名，以及事务内为静态应用增加 sandbox 后端；不新增分类模型、数据库迁移或依赖。当前行为、兼容边界与升级顺序以 [开发说明](../development/web-site-sharing.md) 为准。下文“当前行为”表保留为实施前快照；专用应用域、自定义域、访客提醒和确定性固定通知仍是后续候选。没有部署或修改生产数据。

## 一、研究结论

建议统一用户理解和创建入口，把“静态 / 动态”作为交付能力差异逐步呈现；保留按需后端与独立调度的实现边界。用户说“做个喝水提醒助手”，首先需要明确提醒效果，而不是选择技术产物。一个目标可能同时需要页面、数据记录、定时执行和通知，不能天然归成互斥的四类。

这是一项产品推导，不是外部资料对 LinkSense 架构的证明。Google PAIR 明确要求先识别真实用户问题，并评估更简单的办法；Microsoft HAX 建议遇到意图不明时先澄清；GOV.UK 要求只询问确实必要的信息。[S1][S2][S5] 这些原则支持“结果优先、能力按需”，不能直接证明某项后端方案更快、更便宜或更可靠。

访问地址需要分开决定三个问题：**应用的稳定身份、给人阅读的别名、运行代码所在的安全 origin**。`/app`、`/a` 或省略路径前缀只影响地址表达；路径本身不提供浏览器同源隔离。[S9][S10] 静态应用加后端不应改变逻辑身份，后端项目 ID 不宜决定应用的永久公开身份。统一入口、静态原地增强、独立域和自定义域是不同的工程步骤。

## 四、建议的对话机制

**先形成可修正的目标理解，再问真正影响能力选择的问题。** 对“做个喝水提醒助手”，第一个问题可以是：“关闭页面后也需要收到提醒吗？”选项用结果语言：“需要”“打开页面时提醒就行”“还没想好”。这会影响执行与通知能力；“静态网站 / 内部应用 / 自动化 / 动态应用”要求用户先理解平台内部分类。

用户已经说明“发一个公开链接给同事一起记录”，就不应再询问希望怎样访问；若只说“自己用”，也不自动推断必须安装 LinkSense 应用。**使用范围与发布授权分别理解**：“可能给同事用”“选择 Web 应用”不能自动解释为现在公开。明确要求发布已经足够时直接执行，不再重复批准。只有仍会改变访问权限、数据隔离或通知接收者时，才继续问“谁会用”。这是对上下文利用、必要信息和问题聚焦原则的产品应用。[S2][S3][S5]

**默认值应可见、局部、可改。** 可以复述“我先按个人使用来设计，你可以随时改成多人”；不宜默认开启通知、连接他人账号或替用户确定提醒时间。提醒频率、时区、有效时段、接收者及实际通知渠道，应在启用任务前明确。这里的启用边界是本稿建议；现有产品是否需要额外确认，由实际副作用及既有授权决定。[S4]

**允许目标生成多个协同产物。** 用户确认需要关页后提醒且还想查看记录时，候选方案可以包含记录页面、持久化、调度和通知。计划用一张简短摘要说明“会得到什么、还缺什么、下一步做什么”，避免让用户面对一组孤立的技术选项。若平台没有所需的分钟级调度或访客通知能力，应如实指出缺口，不能用一个前端定时器冒充完成。

上述流程不是要求每次先规划再创建。目标明确、风险低时，可直接生成可撤销的草稿，并在结果中展示采用的关键默认值；只有能力、权限或外部副作用无法判断时才追问。[S3][S4][S6]

### 最小意图模型

由现有 agent 在同一轮理解目标，暂不增加每条消息都调用一次的独立分类模型，也不靠关键词“应用”“提醒”硬分流。建议内部关注以下维度，允许未知，并记录是用户明确说明、已确认答案还是临时假设：

| 维度 | 例子 | 真正改变的选择 |
| --- | --- | --- |
| 使用者与宿主 | 个人/同事/外部访客；独立网页/LS 内/尚不明确 | 平台身份、独立访客、资源授权、分发；“自己用”不能单独决定宿主。 |
| 页面 | 无页面也可以/需要页面或打卡/需要 LS AI 界面 | 是否生成 UI；是否需要平台应用。 |
| 状态 | 临时/刷新保留/跨设备/多人各自数据 | 是否开通存储、会话、权限；持久化不必强制注册，当前可用匿名访客会话。 |
| 执行 | 用户打开后操作/定时执行/需要 AI 判断 | 页面计时、确定性服务端工作或现有 AI 自动化；三者分别评估。 |
| 通知 | 页面内提示/平台结果/已连接渠道/外部访客订阅 | 实际执行时间、接收者、授权、送达；不可只记录一个“需要提醒”的布尔值。 |
| 当前授权与阶段 | 探索/预览/公开发布/启用计划/修改既有应用 | 什么时候生成草稿，什么时候允许产生外部效果。 |

不建议首版新增一套 Intent 数据库或自定义 Codex 生命周期。先复用已持久化的会话与表单答案、已有应用 ID 与配置；明确的业务资源关系再放入相应领域模型。不要只依赖一个会话级“已选动态应用”标签，阻止用户以后调整需求。

澄清依据是“这个未知值会不会实质改变结果、身份、成本或副作用”，而非模型自报某个置信分超过 0.8。外部资料支持先消歧，不提供可直接照搬的 LinkSense 置信阈值。[S2] 不涉及关键差异时先做草稿；涉及关键差异时问一个聚焦问题，再根据答案继续，不能把现有“ask once”理解成以后永远不能问必要的执行细节。

### 喝水助手的具体对话与路由

首次只问一件影响交付的事，例如通过现有 `request_user_form`：

> 这个助手需要在你关掉页面后，仍主动提醒你吗？
>
> - 需要，关闭页面后也提醒：还需设置时间和实际接收方式。
> - 打开页面时提醒就行：先做可操作的页面计时器。
> - 先做页面，提醒稍后决定：先展示草稿，不启用后台执行。

“页面内提醒”和“先看草稿”是当前阶段选择，不是技术类型。一组 radio 的选项要互斥；“提醒+页面”不是互斥选项之一，而是确认提醒以后按用户需要附加页面。需要补充时可以加可选文本字段，首版不为此另写复杂向导。

| 用户进一步说明 | 合理方案 | 当前限制 |
| --- | --- | --- |
| 页面开着时倒计时，刷新不保存 | 无后端 Web 页面 | 浏览器后台节流、页面关闭、锁屏不能承诺持续精确计时；应说明运行边界。 |
| 每次喝水打卡，明天/换设备仍有记录 | Web 页面 + 持久化；根据数据归属使用匿名会话或登录 | 静态沙箱不能靠 localStorage 实现；匿名会话不等于跨设备身份。 |
| 不需要页面，每天某个时间通过已连接渠道提醒我 | 优先既有 LS 自动化，明确计划/时区/接收目标 | 当前每次启动 AI 轮次；简单固定文案的确定性通知执行器是后续性能改进，不是现成功能。 |
| 利用 LS 知识库和 AI 给我调整饮水计划 | LS 应用；按实际需求附加自动化 | 是否需要自定义页面继续按需求判断，不强制再生成公开站点。 |
| 外部访客各自打卡、设置各自的提醒 | Web 应用 + 访客身份/数据 + 访客提醒订阅/执行/送达 | 前两项已有基础；访客与调度通知的连接尚未具备，不能报告整个目标已完成。 |

建议确认后用一条简短、可改的摘要继续：“先做个人饮水打卡页，记录可保存；后台提醒等你选好渠道后启用。”已有授权足够时不再额外加“是否确定”。实际交付卡要分别说明页面可用、数据可用、提醒待配置/已启用，避免一个“应用已完成”掩盖缺失能力。

## 五、统一静态与动态的合理范围

建议从产品上呈现同一个“网页 / 应用”对象及创建入口；用“保存数据”“多人账号”“服务器操作”等能力解释何时需要后端。界面交互、持久化和可信服务端执行是不同维度，不能仅凭“看起来能点、能记录”判定技术管线。

“动态能力更多”不构成所有内容立即配置后端的理由。只有用户目标需要服务端数据、身份、权限或业务逻辑时，才提出并准备相应能力。任务调度和消息送达仍需独立核实；Appwrite 的存在不自动满足这些要求。该建议来自需求优先原则，[S1] 其资源成本、生命周期与性能收益仍需本地测量。

统一入口也不等于已经支持存量静态站点原地升级。地址、数据归属、隔离、会话、旧链接和发布回滚是否可连续保留，必须由代码与迁移设计验证。能力升级失败时，应能说明当前可用状态、缺失条件和恢复方式，不把重新创建默认为用户必须承担的操作。

从产品上，可把静态与动态统一叫 **Web 应用**，包含“页面”“保存数据”“访客账号”“服务器操作”等能力；把 **LS 内应用** 保留为使用平台 AI/资源/身份的宿主，把 **自动化** 保留为可独立使用或组合的执行能力。四者不是同一层级的互斥类型。动态 Web 应用不是平台应用的能力超集，也不是通知能力的超集。

从实现上优先复用现有 `WebSite`、不可变 Release、可选后端与表单链路。后端未开通时不调用 `prepare_backend`，不因为统一产品名而把所有静态页面配置 Appwrite。按需增强需在同一 Web 应用身份上关联后端，并验证升级失败时旧版本仍可运行。既有静态页面的旧地址、既有动态项目/数据/会话、历史独立 origin 全部保留；不批量改运行模式，不静默迁移应用。

推荐分两步：先改善对话澄清、能力表达和交付状态；再实现稳定应用地址与静态加后端的连续升级。后一项需要专门的绑定事务、资源就绪检查、并发与回退测试。当前调研没有授权其实现或数据库变更。

## 六、访问地址：评估 origin、身份与别名

### URL 要解决的三个问题

1. **稳定身份**：内部尽量复用已有 WebSite ID；外部可映射较短、不含业务含义的稳定 public ID。它不随标题、后端或发布版本变化。
2. **可读别名**：可选 `water` 之类的 alias；不要求先起名才能开始制作。改名后保留旧别名指向或受控跳转，不把旧名重新交给别人制造链接接管。
3. **运行与权限边界**：选择主域路径、独立应用域或每应用 origin。浏览器的 origin 由 scheme/host/port 决定，不由路径决定。[S10] ID/slug 的随机性不能代替服务端访问控制。

W3C 的 URI 设计原则要求避免把会变化的实现细节放进永久链接。[S9] 对 LS 的推导是：对外链接不暴露“静态/动态”、Appwrite Project ID、数据库 ID、函数 deployment 或当前 release；稳定入口解析当前已发布版本，版本地址用于明确的预览/审计。不能为了恢复命名的一致性强制迁移旧链接。

作为发布模型的先例，Vercel 把具体部署 URL、稳定生产 URL、分支 URL 与自定义域分开管理。[S14] 这里只借鉴地址与发布解耦，不引入其托管服务或外部依赖。

### 方案比较

以下是部署形态的产品建议，非当前均可用；`example.com`/`example.net` 只作示例。

| 方案 | 例子 | 好处 | 代价和边界 |
| --- | --- | --- | --- |
| 主域路径 | `https://ls.example.com/app/<public-id>` | 沿用已有域名和证书，最容易自部署；当前形态最接近。 | 路径不是 origin 隔离；必须保留可信壳、沙箱和受控 SDK；不能为便利给生成代码主站同源权限。 |
| 单独的应用访问域 + 路径 | `https://apps.example.net/<public-id>`，或一个单独配置的 `apps.example.com` | 一个额外主机名即可承载多个应用，无须泛解析；可把控制台与公开应用外壳分到不同 origin。 | 多个应用仍共享该 origin，仍须沙箱。不同可注册域名还能拉开 site 边界；同一主域的子域只分开 origin，不自动解决 Domain Cookie/same-site 风险。要修改并测试 Host/Origin/CSP/SDK/会话，不能只替换 URL。 |
| 每个应用独立主机 | `https://<public-id>.apps.example.net/` | 原生 origin 级应用隔离；适合未来需要独立浏览器存储、Service Worker、PWA 的运行模式。 | 要管理每应用 DNS/TLS；泛解析/泛证书是批量方案，非逻辑上唯一办法。Cookie、跨域、迁移和滥用治理更复杂；仍不能直接授予 LS 平台身份或保证后台通知。 |
| 自定义域名 | `https://water.customer.example/` | 正式业务可使用自身品牌根地址。 | 应作为已有应用的可选访问绑定，验证归属并管理 TLS/移除与重绑；换域后浏览器 origin 变化，不能保证旧 Cookie/登录状态自动转移。当前尚无该能力。 |

成熟自部署系统也会单独设计公开内容域。GitLab Pages 要求 Pages 域不是 GitLab 实例域的子域：实例为 `gitlab.example.com` 时可以使用兄弟域 `pages.example.com`，实例直接用 `example.com` 时则不能照搬；其默认独立站点域用于减少 Cookie 共享。[S12] 这是其产品的明确约束，不是所有部署都必须原样遵循的 Web 标准；对 LS 的启示是同时审查 origin、父域 Cookie 和应用间隔离。Cookie 不设置 Domain 时为 host-only；`__Host-` Cookie 不允许 Domain。[S13]

这里不因外观更短而判定子域名更快，也不因少一个路径层级而声称性能提升。实际延迟由网络、TLS/缓存、网关和应用资源决定，需测量。另一个域可能新增连接建立开销，不能忽略。

**本题推荐**：

- 对“只有现有 LS 域名/证书”的安装，主域路径作为完整可用的默认入口；`/app` 可以继续保留，是否缩成 `/a` 的优先级很低。
- 对正式对外应用，可选配一个专用应用访问域。若暂时不需要原生浏览器能力，单应用域 + 路径 + 沙箱是值得优先验证的中间方案：不用为每个应用增加 DNS，也与主站分开 origin。这是架构推导，不是已通过安全验收的实现。
- 独立应用 origin 和自定义域作为有具体能力需求时的可选形态。不要让普通创建对话先做部署方式选择，也不要把已有沙箱应用换域当成自动获得原生浏览器能力。

### 地址与生命周期的约束

面向用户只显示一个主访问地址，别名/自定义域放在发布设置；静态加后端不应更换该主地址。确认发布前再设置可读地址即可，内部工作先使用稳定 ID，减少新建时的问题数。

改名、发布新版本、后端恢复不改变应用身份。旧别名是否跳转、跳转到哪一个已验证地址必须由服务端映射决定。停用状态应同时覆盖主地址、历史别名、自定义域、旧版本资源和 API；跳转不能绕过停用。域名映射不接受任意请求 Host 自动注册，不把查询参数里的外部 URL 直接用作跳转目的地。[S11]

跨 origin 更改需单独处理访客登录。当前 Redis 原生会话键虽按后端 ID 保存，但浏览器访问标识 Cookie 是 host-only，换域后不会自动携带。[访客 Cookie](../../apps/api/src/modules/web-site-backends/sandbox-gateway.ts#L44-L72)、[会话键](../../apps/api/src/modules/web-site-backends/visitor-sessions.ts#L20-L44) 因此“数据仍在”和“访客不需重新登录”是两项不同验收；不能为了迁移把 Cookie Domain 放大或在 URL 中传递原生会话/凭据。

## 七、提醒、体验和性能验收

“关页后仍提醒”应拆成三项验收：谁在计划时刻执行、通过什么渠道发送、接收设备能否展示。通知授权状态、浏览器限制和消息展示必须分别观察。[S7][S8] 手机锁屏、离线、浏览器被系统停止、权限拒绝和时区变化，均需在目标设备实测；本文没有取得这些结果。

性能也应按路径比较，而不是预设动态更慢或静态更快。建议记录首个可用预览时间、首次成功完成目标时间、澄清轮数、用户纠正方案比例、后端准备等待及失败率；运行端分别记录首屏可交互时间和首次数据操作耗时。先保留无后端路径，再测量附加能力的实际成本。

面向用户的进度可表达为“正在生成页面”“正在准备数据存储”“还需选择提醒方式”；只有相应能力确实可用后才报告完成。UI 可以先预览，真实提醒的验收仍需完成执行与送达检查。

建议首轮验收集：

- **意图与改口**：明确请求不重复问；模糊“做个助手”能问出关键差异；“我也要页面”“以后给别人用”不造成互斥错误；已有应用更新复用原资源。用固定多语言样例验证工具轨迹，不能只测试指令中是否含某句话。
- **表单体验**：一次聚焦一个关键决策，选项有简短结果说明；选择不自动提交；能取消、不重复创建；键盘和窄屏可用；切换单选与新内容出现不改变用户阅读位置。沿用现有设计系统并覆盖六语言。
- **能力真实性**：未开后端不 provision；刷新保留和跨设备身份分别测试；没有渠道、权限或不支持的计划时显示缺口；访客不能操作作者的计划或通知连接。简单固定提醒与 AI 自动化分别测量 token/运行成本、触发排队和送达延迟。
- **兼容与地址**：以变更前静态/动态/旧 origin 记录测试持续可用；再验证静态增强、别名改名、升级失败回退、发布和停用；换域另测登录、Cookie/CSP/RPC 和新旧地址。不能用“新建应用通过”证明升级安全。
- **实际性能**：记录首次可用预览时间、首次目标成功时间、澄清轮数/放弃率/纠正率，分开 agent 理解、工具准备和构建耗时；运行端测 LCP/INP/CLS 与数据请求。先取得基线，不承诺未测量的提速比例。

最小实施范围可先落在 Runner 路由指令、两份内置 Skill 和交付说明/相应测试；内置 Skill 改动需要重新计算 `BUILT_IN_CAPABILITY_RUNTIME_REVISION`，验证 fingerprint 与旧快照刷新。稳定地址/原地增强、访客提醒、无模型固定通知属于分开的后续能力，不能为第一步一次性重写全部应用系统。
